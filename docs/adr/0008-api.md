# 0008: API(REST + SSE)

- 日付: 2026-09-26
- 状態: 採用

## 背景

Phase 5 で、フロントエンドから使える API を用意する。これまでの `DebateEngine.run` は開廷から判決までを一気に進めるため、ターン単位の進行と、イベントストアからの再開ができなかった。

## 決定

### エンジンを 1 手ずつ進められるようにする
- `DebateEngine` を次の操作に分ける
  - `start`(開廷)
  - `resume`(ストアのイベントから状態を再構築)
  - `collect_evidence`(証拠品の投入、または捜査)
  - `advance`(次の 1 手)
  - `run_to_end`
- 次の手番は状態とモードの進行表から決まる純粋関数 `next_step(state, mode)` で求める。進行位置をエンジンに別途持たせないので、どのプロセスからでも再開できる
- 既存の `run()` は上の操作の組み合わせにした(CLI と評価ハーネスは変更なし)
- 手順違反(証拠品の前に進める、閉廷後の操作など)は `SessionStateError` とし、セッションを中断させない。処理中の例外は従来どおり `SessionAborted` を記録してから送出する

### LLM 呼び出しの記録の分離
- API ではプロバイダごとの並列度制限を効かせるため、`LLMClient` を全セッションで共有する
- `BufferedRecorder.isolated()`(ContextVar)で、バックグラウンドタスクごとに記録を分ける。`asyncio.gather` で作られる子タスクは親のバッファを共有する

### エンドポイント(`/api`)
- 開廷(`POST /sessions`)、証拠品の投入(`PUT …/evidence`、`ResearchReport` をそのまま受け付ける)、捜査(`POST …/research`)、1 手進める(`POST …/advance`)、判決まで(`POST …/run`)、状態(`GET …/{id}`)、イベント(`GET …/events?after=`)、SSE(`GET …/stream`)、法廷記録(`GET …/record`)、計測(`GET …/summary`)
- 捜査と進行はバックグラウンドタスクにして 202 を返す。1 セッションにつき同時に 1 タスクまでで、実行中なら 409 を返す。タスクは開始時に状態をストアから読み直す(受付から開始までのずれを防ぐため)
- セッションがなければ 404、手順違反は 409
- OpenAPI の operation_id を明示する(`createSession` など)。`llm-court openapi` でスキーマを出力できる(Phase 7 の型生成用)
- CORS は `Settings.api_cors_origins`(既定 `http://localhost:3000`)

### SSE
- 依存を増やさず `StreamingResponse` で実装する。流すメッセージは次のとおり
  - `debate`: 永続イベント。`id` は seq
  - `turn`: 発言の開始
  - `token`: 発言のチャンク。保存しない
  - `progress`: 捜査などの進捗
  - `task`: タスクの開始・完了・失敗
- 接続時は、先に購読を始めてから `Last-Event-ID`(または `?after=`)より後の履歴をストアから送る。そのあと新着を seq で重複を除いて送り、取りこぼしを防ぐ
- 判決(`verdict_delivered`)または中断(`session_aborted`)を送ったら閉じる。そのため、その後に出る `task` の完了通知は届かない
- キープアライブの間隔は `Settings.api_sse_keepalive_s`

### PLAN との差分
- PLAN の Phase 5 にある「人間の選択送信」は、選択肢を作る分析官(Phase 6)に依存するため Phase 6 で追加する
- 「テーマ設定」は開廷時の入力に含めた

## 理由

- 次の手番を状態から導けば、進行状況を別に保存せずに済み、「状態はイベントログから再構築できる」という不変条件と一致する
- トークンを保存しないのは、発言の全文が `StatementMade` に残り、トークン列を保存しても情報が増えないため

## 影響

- LLM サーバーの一時的な障害でも、進行中のセッションは中断(`SessionAborted`)になる。再試行・再開の仕組みは必要になったら追加する
- サーバーの再起動時、実行中だったタスクはキャンセルされ、そのセッションは中断として記録される
