# 0007: 評価ハーネス

- 日付: 2026-09-26
- 状態: 採用

## 背景

Phase 4 で、モデル構成やプロンプトの良し悪しを印象ではなく数字で比較できるようにする。何を固定し、何を測り、評価のための LLM 呼び出しをゲームのイベントとどう分けるかを決める必要があった。

## 決定

### 評価仕様
- `llm-court eval <spec.yaml>` で実行する。仕様には次を書く(`backend/eval/specs/example.yaml`)
  - 構成(models.yaml 形式のファイル)
  - テーマと、固定で使う捜査結果
  - 反論の往復数、テーマごとの実行回数、裁判長の再評価回数
  - 任意で参照用裁判長
- 証拠品は構成間で同じ捜査結果(`evidence`、必須)を使う。捜査は検索結果が毎回変わり、比較の雑音になるため。捜査そのものの評価は範囲外とする
- 構成ごとにまとめて実行する(LM Studio のモデル切り替えを減らすため)
- 比較の再現に使う捜査結果は `backend/eval/evidence/` に置いてコミットする

### 裁判長の再評価と参照用裁判長
- 終わったディベートを、同じ裁判長に `judge_repeats` 回評価し直させる。毎回 2 つの提示順で評価する
- 再評価はゲームの状態ではないため、ディベートのイベントには追記しない。`DebateRun.judgings` と `judge_calls`(LLM 呼び出しの計測)として評価結果に保存する
- 参照用裁判長は、仕様で指定したときだけ別の `LLMClient` を作って `judge` 役で採点する。ゲーム本体のコードはこれに依存しない。クラウドのモデルを物差しにする場合も、既存の OpenAI 互換プロバイダと `${ENV}` 展開の api_key で表す
- 1 回のディベートの中断(`SessionAborted`)は記録して続行し、中断数も指標に含める。LLM サーバーへの接続失敗だけは評価全体を止める

### 指標
- 裁判長の一貫性
  - 順序反転率: 提示順を入れ替えた評価の組のうち、勝者が食い違った割合
  - 再評価の安定性: 同じログの判定が最頻の判定と一致した割合
  - 点差のばらつき: 各評価の点差の標準偏差
  - 参照用裁判長との一致率
- 引用
  - 存在しない証拠品の率: 存在しない証拠品 ID ÷ 出典の総数
  - 証拠品にない引用の率: 証拠品にない引用 ÷ 照合対象の「」引用の総数(分母は `count_checked_quotes` で数える)
  - 出典のない発言の率
- 構造化出力: 失敗率、1 回あたりの再試行数(役割別の内訳あり)。再評価の呼び出しも含む
- レイテンシ: 論者の発言ごとの TTFT と総時間の p50 / p90 / 最大、tok/s、ディベート 1 回の所要時間
- 補助: 平均字数と目安字数との比、発言あたりの主張数、判決の分布

### 引用の指標は本文から計算し直す
- 引用の指標は、イベントに記録された `CitationIssuesDetected` ではなく、発言本文を現在の検査規則で検査し直して求める。規則を直したときに、ディベートをやり直さずに過去の実行と比べられるようにするため
- ただし、ディベート中の裁判長には記録時の規則による検査結果が渡っている点に注意する
- `llm-court eval-report <結果ディレクトリ>` で、保存済みの結果(`result.json` と `debates/*.jsonl`)から指標とレポートを作り直せる

### 出力
- `data/eval/<日時>-<名前>/` に次を出力する
  - `runs.csv`(ディベートごと)
  - `turns.csv`(発言ごと)
  - `summary.csv`(構成ごと)
  - `report.md`(構成を横に並べた比較表と指標の定義)
  - `result.json`(イベントを除いた全結果)
  - `events.db`
  - `debates/*.jsonl`

## 理由

- 証拠品を固定すると、構成の差を論者と裁判長の能力の差に絞れる
- 再評価をイベントに入れないことで、「ゲーム状態の真実はイベントログ」という不変条件を評価の都合で崩さずに済む

## 影響

- サンプル数が少ないうちは差の有意性を判断できない。レポートにもその旨を書く
- 各構成で論者と裁判長が同じモデルの場合、自己選好バイアスは指標に表れない。参照用裁判長との一致率で補う
