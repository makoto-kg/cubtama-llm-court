# 0012: 裁判型の事件生成パイプライン

- 日付: 2026-09-26
- 状態: 採用

## 背景

Phase 8 で、裁判型の架空の事件を事前に生成して保存する。LLM に事件を一発で書かせると、参照の食い違いや解けない事件になりやすい。段階的に生成し、規則と solver で検証する必要があった。

## 決定

### ドメインモデル(`domain/case.py`)
- PLAN §4 の `Case` / `HiddenTruth` / `Testimony` / `WitnessScript` / `LearningPoint` を具体化した
- 補助として次を加えた
  - `Person`、`TimelineEvent`、`Lie`
  - `CaseEvidence`、`TestimonyLine`、`CollapseCondition`
  - `Contradiction`(嘘・証言の行・証拠品・学習ポイント・罠の対応)
  - `Trap`、`CaseQuestion`
  - `SolverRun`、`CaseValidation`、`CaseGeneration`、`CheckIssue`
- プレイヤーと solver に渡すのは `Case.public_view()`(`CasePublic`)だけにする
  - 含めるもの: 概要・選択肢だけの問い・人物・証拠品・`lie_id` を除いた証言
  - 含めないもの: 学習ポイント・真相・台本・矛盾・正解

### 段階的な生成(`scenario/generator.py`)
- 手順
  - 捜査(`ResearchPipeline` を再利用。`--evidence` で既存の捜査結果も使える)
  - 学習ポイント
  - 真相(人物・時系列・嘘)
  - 資料(証拠品・証言・台本・矛盾・問い)
  - 罠
  - 整合性チェック
  - solver 検証
- LLM は scenario_writer 役(生成)と solver 役(検証)
- 学習ポイントの出典は、検証済みの事実のキー(`EV-01-f2`)で指定させ、引用はコードで事実から取る。存在しないキーの出典は捨て、出典のない学習ポイントは除く
- LLM には下書きのキー(`p1`・`e1` など)で互いを参照させ、正式な ID の採番と参照の組み立てはコードで行う。文中に残ったキーは名前や正式な ID に置き換える
- 台本の崩れる条件は、矛盾(証拠品)と `witness_reaction` からコードで組み立てる。同じ対応を二重に書かせない
- 作り直しは 2 層にする
  - 段階内: 参照が解決できない(`DraftError`)、各嘘がちょうど 1 行・1 件の矛盾に対応していない、などは、問題点を伝えてその段階だけ作り直す(`draft_retries`)
  - 全体: 規則のチェックで問題があれば、問題のある最も早い段階から作り直す。solver が解けなければ資料(段階 3)から作り直す(`max_regenerations`)
  - solver が解けなかったときは、solver の実際のつきつけを具体的な指示にして伝える
    - 別の証拠品で気づかれた → 決め手を一意にする
    - 嘘でない証言が矛盾に見えた → 真実の証言を証拠品と合わせる
    - 気づかれなかった → 証拠品の記載を具体的にする
- 上限まで作り直しても解けない事件も、調べられるように保存し、CLI は終了コード 1 を返す

### 整合性チェック(`scenario/checks.py`、規則ベース)
- 参照切れ
- 時系列
  - 順番の重複
  - 同じ時刻に同じ人物が別の場所にいる
- 嘘の数
- 嘘 ⇔ 証言の行 ⇔ 矛盾の 1 対 1 対応
- 学習ポイントの対応漏れ(どの矛盾にも使われない)
- 台本の崩れる条件の不足
- 問いの正解の範囲
- 公開する文への非公開 ID の漏れ
- 罠が正解の証拠品と重なる
- 問題には、作り直す段階を付ける

### solver 検証(`scenario/solver.py`)
- 公開情報だけを渡し、順序付きのつきつけ(証言の行と証拠品)と問いの答えを出させる
- 採点
  - 見つけた矛盾
  - 全矛盾を見つけた手数
  - 余分な指摘
  - 行は当てたが証拠品が違う(`near_misses`、決め手が一意でない疑い)
  - 問いの正誤
- 判定
  - `solved`: 1 回でも全矛盾を見つけ、問いに正答した
  - `unique`: 全回の答えが一致し、余分な指摘がない
  - `solve_rate`: 解けた回の割合
- 実行回数は `Settings.scenario.solver_runs`

### 保存と CLI
- 生成した事件は `Settings.scenario.case_dir`(`data/cases/<id>.json`)に保存する。プレイ時は読み込むだけにする
- 事件は事前処理の成果物で、ゲームの状態ではない。そのためイベントログには入れない。生成の LLM 呼び出しは件数・トークン・時間・作り直しの回数に集計して `Case.generation` に残す
- CLI
  - `llm-court case generate "<テーマ>" [--evidence]`
  - `llm-court case validate <id>`(検証をやり直して更新する)
  - `llm-court case list`

## 理由

- ID と参照をコードで組み立て、LLM には内容だけを書かせると、参照の食い違いが生成のたびに起きても機械的に直せる
- 解けるかどうかの判定を LLM の自己申告ではなく、公開情報だけを見た別の呼び出しの結果にすると、「真相を知っている書き手には自明だが、プレイヤーには解けない」事件を除ける

## 影響

- gpt-oss-20b での実測: 生成 1 件あたり約 6 分(LLM 呼び出し約 17 回)。資料の作り直しが上限近くまで発生した
- solver の結果は揺れる。生成時に 2 回中 1 回解けた事件が、再検証では 2 回とも解けなかった。安定して解ける事件にするには、solver の回数を増やして `solve_rate` で判定するか、より強いモデルに割り当てる必要がある
- 「学習ポイントの知識を当てはめないと見抜けないか」は規則では検証できない。数値の比較だけで解けてしまう矛盾が生成されることがある。知識を与えない solver との比較などで確かめる方法が今後の課題
