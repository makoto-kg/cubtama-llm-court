# 0014: 完全オフラインモード(裁判型)

- 日付: 2026-09-27
- 状態: 採用

## 背景

Phase 10 の着手にあたり、ユーザーから「フロントエンドだけで、バックエンドなしで遊べるモード」の要望があった。事前に LLM でシミュレーションした結果を使う。対象は裁判型に限った。

ディベートの対戦は、人間の選択で展開が分岐する。事前に生成する量が大きいので、今回は対象外とした。

裁判型は、LLM を使う部分が証人の応答だけである。
- 事件・選択肢(規則)・正誤・減点・解説は、LLM なしで決まる(ADR 0013)
- 起こりうる行動は有限で、事件 1 件あたり数十件

## 決定

### オフラインパック(`backend/src/llm_court/offline/`)
- 事件 1 件 = 1 JSON(`OfflinePack`)。内容は次のとおり
  - 公開ビュー(`CasePublic`)
  - 進行に必要な非公開の情報(`OfflineAnswers`: 矛盾の行と証拠品、罠と選びたくなる理由、問いの正解)
  - 解説(`build_explanation` の結果)
  - モードの値(ゲージ・減点・選択肢の数)
  - 行動キーごとの証人の応答(`OfflineResponse`)
  - 生成の記録(`OfflineMeta`)
- 真相の要約は解説に含まれる。台本(人物像・隠している事実)は応答の LLM 呼び出しの記録にだけ入る
- 行動キーは `present:<行>:<証拠品>` / `probe:<行>`
- 一覧は `index.json`(`OfflineIndex`)
- 置き場所は `frontend/public/offline/`(`settings.offline_output_dir`)。静的ファイルとして SPA に同梱する

### 事前シミュレーション(`llm-court offline export`)
- 対象は、分析官が並べうる全行動
  - 矛盾のある証言の、全行 × 全証拠品の「つきつける」
  - 全行の「ゆさぶる」
- 証人の応答は履歴なしで生成する
  - オフラインでは、行動をどの順で選んでも同じ応答を返すため
  - オンライン(Phase 9)は直近のやりとりを渡すので、応答の文脈は少し弱くなる
- 各応答を逸脱の検査(ADR 0013)にかける
  - 逸脱があれば `--retries` 回まで作り直す
  - 逸脱の最も少ない応答を採用する
  - 残った逸脱の数はパックの `meta.deviations` に記録する
  - 事前に作れる利点として、オンラインより応答の品質を上げられる
- 採用した応答の LLM 呼び出しの記録も入れ、閉廷後の思考ログとして見せる
- LLM は `llm/` 層の witness 役・judge 役で呼ぶ。並列度はプロバイダごとのセマフォに任せる

### フロントエンド(API を呼ばない)
- 進行ロジックを TypeScript に移植した(`src/lib/offline/`)
  - 規則の分析官(`analyst.ts`)
  - 状態の遷移(`engine.ts`)
  - seed 付きの乱数(`prng.ts`)
  - 選択肢の並びは Python 版と同じにはならないが、同じ seed なら再現できる
- 状態の真実は「行動の列」とした
  - `localStorage` に保存し、状態は `replay` で作り直す(イベントログの考え方を踏襲)
  - 再読み込みで続きから遊べる
  - パックが更新されて再生できないときは、最初からにする
- 「解説に異議あり」も行動として保存する。JSON で書き出せる
- 表示は Phase 9 の画面を分割して共有した
  - `TrialBoard`: 表示だけ
  - `TrialScreen`: オンライン
  - `OfflineTrialScreen`: オフライン
  - オフラインのエンジンは `TrialView` と同じ形を作る
- 証人の応答は、事前生成の全文を少しずつ表示して「流れる」ように見せる
- 画面
  - `/offline/`: 一覧
  - `/offline/trial/?case=<id>`: 裁判
- `NEXT_PUBLIC_OFFLINE_ONLY=1` でビルドすると、タイトルがオフラインの一覧になり、設定画面への導線を出さない(配布用)

### 型の共有
- パックは API では返さない
- それでも手書きの型を作らないために、`create_app` の OpenAPI に `OfflinePack` / `OfflineIndex` の JSON Schema を components として追加した
- `pnpm gen:api` で TypeScript の型が生成される

### 同梱データ
- solver の検証に合格した事件 2 件のパックを、`frontend/public/offline/` にコミットする
  - `eval/evidence/` と同じく、すぐ遊べるサンプルとして扱う

## 理由

- 裁判型では LLM の役目が証人の演技に限られる。全行動を事前に生成すれば、ゲームとしての体験はオンラインとほぼ同じになる
- 進行をブラウザに移しても、判定は事件のデータと規則で決まるので、Python 版と同じ振る舞いを移植でテストできる

## 影響

- 正解(矛盾・問いの答え)がブラウザに届く。開発者ツールで見られるが、クライアントだけのゲームとして許容する
- 判定ロジックが Python と TypeScript の二重になる。規則を変えるときは両方を直す
  - 両方に同じ観点の単体テストを置いている(`test_trial.py` / `engine.test.ts`・`analyst.test.ts`)
- 事件 1 件のパックは、応答数 × 2(証人・判定)回以上の LLM 呼び出しで作る
- パックのサイズは、LLM 呼び出しの記録(プロンプト全文)を含むため数百 KB になる
