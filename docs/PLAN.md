# LLM法廷バトルゲーム 実装プラン

> 仮称: `llm-court`
> このファイルは Claude Code が実装を進めるためのマスタープランです。フェーズ順に実装し、各フェーズの「完了条件」を満たしてから次へ進むこと。

---

## 0. プロジェクト概要

### 0.1 コンセプト

逆転裁判のような「法廷バトルADV」の雰囲気で、LLM がテーマについて論戦するゲーム。
キャラクター・UI・演出はすべてオリジナルとし、既存作品の素材やデザインは模倣しない。

- **対戦形式**
  - LLM vs LLM(観戦・比較検証)
  - 人間 vs LLM(人間はセリフを全文入力せず、分析官LLMが提示する「矛盾点の選択肢」から選ぶ)
- **モード**
  - **ディベート型**:現実のテーマを Web 検索で最新情報まで深掘りする。正解はなく、論理と説得力で裁判長が判定する
  - **裁判型**:LLM が架空の事件・証拠・真相を生成し、プレイヤーは推理を通じてテーマを学ぶ。対象は「ある程度の前提知識がある人」

### 0.2 技術方針(確定事項)

| 項目 | 方針 |
|---|---|
| LLM | OpenAI 互換 API のみに依存。まずは**完全ローカル**(LM Studio / llama.cpp server 等) |
| 想定マシン | AMD Ryzen AI Max+ 395 / 128GB(GPU 割当 64GB〜)。帯域が制約なので MoE モデルが主力 |
| Backend | Python(FastAPI) |
| Frontend | Next.js(App Router, TypeScript) |
| 構成 | Frontend と Backend を完全分離したモノレポ。最初の一歩は Backend のみ |
| 検索 | セルフホストの SearXNG + 自前の本文取得・抽出 |

### 0.3 なぜ Backend を Python にするか

Next.js の Route Handlers だけでも実装は可能だが、以下の理由で Python を採用する。

- 本文抽出(trafilatura 等)、評価・集計、将来の埋め込み処理などのエコシステムが Python に厚い
- LLM 呼び出しの検証スクリプトや評価ハーネスを同じコードベースで書ける
- ゲームロジックを UI から独立させることで、CLI・API・テストから同じエンジンを叩ける

Next.js は純粋なフロントエンドとし、BFF 層は持たない(必要になった時点で再検討)。

## 1. 設計原則

1. **ゲーム状態の真実はエンジンが持つ**。LLM の出力は必ず Pydantic で検証した「型付きイベント」としてのみ状態に反映する
2. **イベントソーシング**。法廷の進行はすべて追記専用のイベントログとして記録し、状態はログから再構築できるようにする。リプレイ・検証・デバッグ表示はすべてこのログを使う
3. **役割(Role)とモデル(Model)を分離**。コードは役割名で LLM を呼び、どのエンドポイント・モデルを使うかは設定ファイルで決める。モデル名をコードにハードコードしない
4. **能力フラグで互換性の差を吸収**。構造化出力・ツール呼び出し・ストリーミングの対応可否をプロバイダ設定に持ち、呼び出し側で分岐する
5. **文脈を短く保つ**。討論ログ全文や証拠品本文を毎回渡さず、構造化した主張ログと要約済み証拠品を渡す。固定プロンプトは先頭に置き、サーバー側 KV キャッシュの再利用を狙う
6. **リアルタイム処理と事前処理を分ける**。事件生成・検証など遅くてよい処理は大きなモデル+推論あり、プレイ中のセリフ生成は速いモデル+推論控えめ
7. **計測を最初から組み込む**。全 LLM 呼び出しでレイテンシ、トークン数、構造化出力の成否、リトライ回数を記録する。デバッグ表示はゲームの機能(「思考ログ」)として後で UI に出す
8. **プロンプトはコードではなくファイル**。テンプレートとして管理し、バージョンをイベントに記録する
9. **出力言語は日本語**。プロンプト・生成テキストとも日本語を基本とする

## 3. 技術スタック

### Backend

- Python 3.12+、パッケージ管理は **uv**
- FastAPI + Uvicorn(API は Phase 5 以降)
- Pydantic v2 / pydantic-settings
- openai 公式 SDK(`base_url` を差し替えて OpenAI 互換サーバーに接続)
- httpx(非同期 HTTP)、trafilatura(本文抽出)
- Jinja2(プロンプトテンプレート)
- Typer + Rich(CLI とログ表示)
- SQLite(イベントストア。SQLAlchemy 2.0 async + aiosqlite)
- 品質: ruff(lint/format)、pyright(型チェック strict 寄り)、pytest + pytest-asyncio
- 構造化出力: 自前の薄いラッパーを実装(能力フラグに応じて `response_format: json_schema` → JSON モード → プロンプト指示+検証+リトライの順にフォールバック)

### Frontend(Phase 7 以降)

- Next.js(App Router)+ TypeScript strict
- Tailwind CSS
- 状態管理: Zustand(クライアントのゲーム状態)
- API 型: Backend の OpenAPI から `openapi-typescript` で型生成
- ストリーミング受信: SSE(EventSource)
- テスト: Vitest + Playwright(E2E は最小限)

### インフラ

- SearXNG(docker compose でローカル起動、JSON 出力を有効化)
- 推論サーバー: 開発初期は LM Studio。並列リクエストが必要になった段階で llama.cpp server(並列スロット設定)を検討

## 4. ドメインモデル(初期案)

実装時に Pydantic モデルとして `domain/` に定義する。フィールドは実装しながら調整してよいが、変更時は ADR を残す。

### 共通

- `Topic`: テーマ文、モード、論点の説明
- `Evidence`(証拠品): `id`、`title`、`source_url`、`retrieved_at`、`summary`、`key_facts[]`
  - `KeyFact`: `text`、`quote`(取得本文に実在する抜粋)、`quote_verified: bool`
- `Statement`(発言): `id`、`speaker`、`text`、`cited_evidence_ids[]`、`turn`
- `Claim`(主張): 発言から抽出した個々の主張。`statement_id`、`text`、`kind`(事実主張/価値判断/推論)、`cited_evidence_ids[]`
- `ContradictionCandidate`(矛盾候補): `target_claim_id`、`evidence_id | other_claim_id`、`type`、`explanation`、`strength`(strong/weak/trap)
  - `type`: `self_contradiction` / `evidence_conflict` / `logical_leap` / `definition_shift` / `fabricated_citation`
- `JudgeScore`: ルーブリック各項目の点数、根拠、評価時の発言順

### 裁判型

- `Case`: 事件全体
- `HiddenTruth`: 時系列、各人物の行動、誰がどこで嘘をつくか(プレイヤーには非公開)
- `Testimony`: 証人の証言と、仕込まれた矛盾への参照
- `WitnessScript`: 証人が隠す事実、嘘の台本、崩れる条件(どの証拠品で崩れるか)
- `LearningPoint`: 決め手となる現実の知識、出典、関連する誤解(罠の選択肢の素)、「古い知識」かどうか

### イベント(追記専用ログ)

`SessionStarted` / `EvidenceCollected` / `StatementMade` / `ClaimsExtracted` / `ContradictionsProposed` / `ObjectionRaised` / `ObjectionResolved` / `JudgeScored` / `VerdictDelivered` / `PenaltyApplied` / `LLMCallRecorded` など。
すべてのイベントに `session_id`、`seq`、`timestamp`、生成に使った `role`・`model`・`prompt_version` を持たせる。

## 5. 役割とモデル割り当て

### 役割一覧

| 役割 | 仕事 | 処理区分 |
|---|---|---|
| researcher(捜査官) | 検索クエリ生成、証拠品の要約・構造化 | 事前 |
| debater(論者) | 主張・反論の生成。証拠品 ID の引用必須 | リアルタイム |
| claim_extractor | 発言から主張を構造化抽出 | リアルタイム |
| analyst(分析官) | ディベート型: 矛盾候補の抽出、罠の選択肢生成(LLM)。裁判型: 事件データからの選択肢の組み立て(規則。LLM を使わない) | リアルタイム(先行実行) |
| advocate(代弁者) | 人間が選んだ選択肢をセリフに清書 | リアルタイム |
| judge(裁判長) | ターン評価・最終判決。裁判型では事件の概要の漏れと、証人の台本逸脱の判定も担う | リアルタイム |
| scenario_writer | 裁判型の真相・証拠・証言の生成 | 事前 |
| witness(証人) | 台本の範囲内で即興証言 | リアルタイム |
| solver(解答者) | 生成された事件を解いて検証 | 事前 |

### `config/models.yaml` の形(例)

```yaml
providers:
  local:
    base_url: http://localhost:1234/v1
    api_key: "not-needed"
    capabilities:
      json_schema: true
      tool_calling: false
      streaming: true
    max_concurrency: 2

models:
  heavy:            # 大きめの MoE。事前処理・裁判長・分析官
    provider: local
    model: "<LM Studio 上のモデル ID>"
    reasoning: high
  fast:             # 速い MoE。セリフ生成
    provider: local
    model: "<LM Studio 上のモデル ID>"
    reasoning: low

roles:
  researcher: heavy
  scenario_writer: heavy
  solver: heavy
  judge: heavy
  analyst: heavy
  claim_extractor: fast
  debater: fast
  advocate: fast
  witness: fast
```

- 常駐モデルは原則 2 つまで(ロード切り替えを避ける)
- 論者と裁判長は別モデルに割り当てる(自己選好バイアス対策)
- 将来、比較検証のためにクラウドの `provider` を追加できる構造を保つ(ゲーム本体は完全ローカルが前提)

### Phase 0: リポジトリ基盤

**目的**: 以降の開発を回せる土台を作る。

- `infra/docker-compose.yml` で SearXNG を起動(JSON 出力を有効化した設定ファイル同梱)
- ルートと backend の `CLAUDE.md` を作成(§8 参照)

**完了条件**: `uv run llm-court --help` が動く。SearXNG に curl で検索して JSON が返る。

### Phase 1: LLM クライアント層

**目的**: どの OpenAI 互換サーバーでも同じように呼べる、計測付きの LLM 層を作る。

- `LLMClient`: 役割名を受け取り、設定からプロバイダ・モデルを解決して呼び出す
- ストリーミング対応(非同期イテレータで文字列チャンクを返す)
- 構造化出力 `generate_structured(role, prompt, schema: type[BaseModel])`
  - 能力フラグに応じて json_schema → JSON モード → プロンプト指示の順に試す
  - Pydantic で検証し、失敗時はエラー内容をフィードバックして再試行(上限回数は設定)
  - 推論モデルの思考部分やコードフェンスの混入を除去する前処理
- プロンプトテンプレート読み込み(Jinja2)、テンプレートのバージョン(ファイルのハッシュ)を返す
- 全呼び出しの計測記録: 開始〜初トークン時間、総時間、入出力トークン数、tok/s、構造化出力の成否・リトライ回数
- 並列度制御(プロバイダごとのセマフォ)
- **ベンチマーク CLI**: `llm-court bench` で各役割のモデルに対し、日本語の自由生成と構造化出力を N 回ずつ実行し、速度と成功率を表示

**テスト**: 録画済み応答を返すフェイククライアントで、フォールバック・リトライ・前処理を単体テスト。実サーバーを使うテストは `integration` マーカー。

**完了条件**: ローカルの LM Studio に対して `bench` が動き、構造化出力の成功率とレイテンシが表で出る。

---

### Phase 2: 捜査パイプライン(証拠品化)

**目的**: テーマから最新情報を集め、引用の実在が検証された証拠品を作る。

- researcher がテーマから検索クエリを複数生成
- SearXNG で検索 → httpx で本文取得 → trafilatura で抽出(タイムアウト・サイズ上限・robots 配慮)
- 重複 URL・類似ページの除去(初期は URL とタイトルの正規化で十分)
- researcher が本文から `Evidence` を構造化生成
- **引用検証**: `KeyFact.quote` が取得本文に実在するかを正規化した文字列照合で確認し、`quote_verified` を設定。未検証の事実は証拠品から除外または明示
- 取得本文はローカルにキャッシュ(再実行時の再取得を避ける)
- CLI: `llm-court research "<テーマ>"` で証拠品一覧を表示・JSON 保存

**完了条件**: 任意のテーマで 5〜10 個の証拠品が生成され、各事実の引用検証結果が表示される。

---

### Phase 3: ディベートエンジン MVP(LLM vs LLM、CLI)

**目的**: 構想の成否を左右する「議論の質・構造化の安定性・待ち時間」を実測する。**ここが最初のマイルストーン**。

- イベントストア(SQLite、追記専用)と状態の再構築
- 進行ステートマシン: 開廷 → 捜査(Phase 2 を呼ぶ)→ 冒頭陳述 → 反論 × N 往復 → 最終弁論 → 判決
- debater: 肯定側/否定側。発言には `cited_evidence_ids` を必須とし、存在しない ID や証拠品にない内容の引用を検出して記録
- claim_extractor: 各発言から `Claim` を抽出してイベント化
- debater に渡す文脈は「証拠品の要約」+「これまでの主張ログ」(発言全文は直近のみ)
- judge:
  - ルーブリック採点(論理の一貫性、証拠の使い方、反論の的確さ、説得力)
  - 発言順を入れ替えて 2 回評価し、不一致なら引き分け扱い
- モード定義の枠組み(`modes/debate.py`)を用意し、ルーブリック・矛盾タイプ・勝利条件をモード側に持たせる
- 出力: イベントログ(JSONL)と、人間が読める Markdown の法廷記録
- CLI: `llm-court debate "<テーマ>" --rounds 3`。進行をストリーミングで表示し、最後に計測サマリ(ターンごとの待ち時間、総トークン、構造化失敗数)

**完了条件**: 完全ローカルで、テーマ入力から判決までが 1 コマンドで完走する。

---

### Phase 4: 評価ハーネス

**目的**: 感覚ではなく数字でモデル・プロンプトを比較できるようにする。

- `llm-court eval` で同一テーマ群に対し複数回のディベートを実行
- 指標:
  - 裁判長の一貫性(同じログを複数回評価したときのばらつき、順序入れ替えでの判定反転率)
  - 引用捏造率(存在しない証拠品 ID、証拠品にない内容の引用)
  - 構造化出力の失敗率・リトライ率
  - ターンあたりのレイテンシ分布
- 結果を CSV / Markdown レポートで出力
- 設定で「参照用裁判長」を追加できるようにする(開発時のみ任意でクラウドモデルを物差しとして使える構造。ゲーム本体の依存にはしない)

**完了条件**: 2 つのモデル構成を比較したレポートが生成できる。

---

### Phase 5: API 化

**目的**: フロントエンドから使える API を用意する。

- FastAPI アプリ
  - REST: セッション作成(テーマ設定を含む)、捜査開始、ターン進行、ログ取得
  - 人間の選択送信は、選択肢を作る分析官に依存するため Phase 6 で追加する(ADR 0008)
  - SSE: セリフのストリーミング、イベント通知
- セッション管理(イベントストアから状態を再構築)
- 長時間処理(捜査・事件生成)はバックグラウンドタスク化し、進捗を SSE で通知
- OpenAPI スキーマを整備し、`frontend` での型生成に備える
- CORS 設定(ローカル開発用)

**完了条件**: curl と SSE クライアントだけで、LLM vs LLM のディベートを最後まで進められる。

---

### Phase 6: 分析官と人間 vs LLM

**目的**: 「選ぶだけで本格的なディベート」を成立させる。

- analyst: 相手の最新発言の主張と、主張ログ・証拠品を照合して `ContradictionCandidate` を生成
  - 強い指摘・弱い指摘・罠(実は矛盾ではない)を混ぜて 3〜5 個
  - 選択は「どの主張に」「何をつきつけて」「どの論法で」の組み合わせとして提示
- 先行実行: 相手の発言生成完了と同時に analyst を走らせ、プレイヤーが読んでいる間に候補を用意
- advocate: 人間が選んだ候補を、人間側のセリフとして清書(文体を揃えて裁判長の文体バイアスを減らす)
- ペナルティゲージ: 罠や弱い指摘を選ぶと減少、ゼロで敗北
- 「ゆさぶる」相当の軽い質問アクションも選択肢として用意
- 引用捏造が検出された発言は、自動的に `fabricated_citation` タイプの強い候補として提示
- API: 選択肢の取得と人間の選択送信のエンドポイントを追加(Phase 5 から移動)。選択はイベントとして記録する
- CLI での簡易プレイ(シナリオ検証用): `llm-court play` でエンジンを直接動かし、選択肢を番号で選んで人間 vs LLM を進める。`--reveal` で強さを事前表示、`--resume` で再開(ADR 0010)

**完了条件**: API 経由で人間 vs LLM の 1 試合を最後まで遊べる。analyst の候補精度(罠の混入率、強い候補の妥当性)を評価ハーネスで測れる。

---

### Phase 7: Frontend MVP

**目的**: 法廷バトル ADV として遊べる画面を作る。

- `frontend/` に Next.js(App Router)プロジェクトを作成、OpenAPI から型生成
- 画面:
  - タイトル・モード選択・テーマ入力
  - 捜査画面(収集中の証拠品が進捗とともに増えていく)
  - 法廷画面: キャラクター立ち絵(オリジナル、初期は仮素材)、テキストボックスのタイプライター表示(SSE ストリームをそのまま表示してレイテンシを隠す)、証拠品ファイル、選択肢 UI、ペナルティゲージ
  - 判決画面と法廷記録
- 「異議あり」系のカットイン演出(オリジナルデザイン)
- **思考ログパネル**: LLM への入力、生出力、パース結果、トークン数、レイテンシをゲーム内の演出として表示(開発時の検証画面を兼ねる)
- 設定画面: 役割ごとのモデル割り当ての確認(編集は後回しで可)

**完了条件**: ブラウザで LLM vs LLM の観戦と、人間 vs LLM の対戦が最後まで遊べる。

### Phase 8: 裁判型 — 事件生成パイプライン(事前処理)

**目的**: 解ける・学べる架空の事件を生成する。

- 生成は段階的に行う(一発生成しない):
  1. テーマから `LearningPoint` を選定し、検索で裏付けを取る(Phase 2 を再利用)
     - 前提知識のある人向けに、「よくある誤解」と「最近覆った古い知識」を優先的に収集
  2. `HiddenTruth`(時系列・人物・嘘の配置)を生成。矛盾を見抜くのに LearningPoint の知識の**適用や組み合わせ**が必要になるよう設計
  3. 真相から証拠品・証言・`WitnessScript` を派生
  4. 各矛盾に対し、罠の選択肢を「よくある誤解」から生成
- 整合性チェック(ルールベース): 時系列の矛盾、参照切れ、LearningPoint と矛盾の対応漏れ
- solver による検証: 公開情報のみを渡して解かせ、解けるか・答えが一意か・何手で解けたかを記録。解けない場合は該当ステップから再生成
- 生成済み事件はファイルとして保存し、プレイ時は読み込むだけにする
- CLI: `llm-court case generate "<テーマ>"`、`llm-court case validate <case_id>`

**完了条件**: 任意のテーマで、solver が解ける事件が生成・保存される。

---

### Phase 9: 裁判型 — プレイ

**目的**: 生成した事件を法廷バトルとして遊べるようにする。

- witness: `WitnessScript` の範囲で即興証言。「ゆさぶる」には言い逃れ、正しい証拠品をつきつけられたら崩れる
  - 崩れるべきか(正解の組か)はコードが決め、LLM には演技だけをさせる
  - 証言の行は事件のデータのまま表示する(LLM で言い換えない)
  - 台本からの逸脱(隠すべき事実の漏洩、崩れるべきでない場面での自白、崩れるべき場面で崩れない)を judge 役が検出して記録する
  - 誤検出を減らすため、判定には応答からの引用を付けさせ、応答中にある引用だけを採用する
- 裁判型の analyst: 仕込まれた矛盾が正解として既知なので、LLM を使わず規則で選択肢を組み立てる
  - 罠は Phase 8 の事件生成で作ってあるので、ここでは選んで並べるだけ(生成はしない)
  - 構成: 正解の組・罠の組・はずれの組・ゆさぶる。提示順はセッションと手番で決まる順に混ぜる
- 進行: 証言ごとに尋問し、全矛盾を解いたら最後の問いに答えて閉廷する。ゲージが尽きても解説へ進める
- 解説パート: 事件解決後に LearningPoint を出典付きで提示。正解の理由と「なぜその罠を選びたくなるか」を説明
  - 出典のない説明を混ぜないため、LLM に書かせず事件のデータから組み立てる
- 「解説に異議あり」: プレイヤーが解説の誤りを報告できる機能(報告はイベントとして保存)
- 閉廷までは、事件の非公開の情報(真相・台本・正解)・選択肢の強さ・LLM 呼び出しの入出力を API で伏せる。閉廷後は思考ログとして公開する
- CLI: `llm-court trial <case_id>`(検証用の簡易プレイ)、`llm-court eval-trial <case_id...>`(自動プレイヤーによる逸脱率の評価)
- Frontend に裁判型の画面・演出を追加
- 詳細は ADR 0013

**完了条件**: 生成済みの事件を最初から解説まで遊べる。証人の台本逸脱率を評価ハーネスで測れる。

### Phase 10: 発展

優先度は Phase 9 完了時点で再検討する。

- プレイヤーモデル: つまずいた LearningPoint を記録し、次の事件で重点的に扱う適応型難易度(初期は難易度選択)
- LLM vs LLM のリーグ戦・リーダーボード(モデル構成の比較をゲームとして見せる)

- 推論サーバーの並列化チューニング(llama.cpp server の並列スロット等)
- 難易度の実測調整(プレイヤーの正答率ベース)

## 7. リスクと対策

| リスク | 対策 |
|---|---|
| ローカルモデルの日本語議論の質が不足 | Phase 1 の bench と Phase 3 で早期に実測。モデル差し替えは設定のみで可能にしておく |
| 構造化出力が不安定 | 能力フラグ+多段フォールバック+検証リトライ。失敗率を常時計測 |
| prefill が遅く待ち時間が長い | 文脈の圧縮(主張ログ・要約証拠品)、固定プロンプトの先頭配置、先行実行、タイプライター演出 |
| 裁判長のバイアス | 論者と別モデル、順序入れ替え評価、ルーブリック、代弁者による文体の統一 |
| 引用の捏造 | 証拠品 ID 必須化と本文照合。捏造自体をゲーム内の「偽証」として扱う |
| 生成事件が解けない・破綻する | 真相先行の段階生成、ルールベース整合性チェック、solver 検証と部分再生成 |
| 解説の事実誤り | LearningPoint の出典必須化、引用検証、プレイヤーからの異議報告 |
| モデル切り替えの遅さ | 常駐モデルを 2 つまでに制限し、役割はその中で割り振る |

## 8. Claude Code 向け運用ルール

### ルート `CLAUDE.md` に書くこと

- プロジェクト概要(本ファイル §0 の要約)と `docs/PLAN.md` への参照
- 現在のフェーズと完了済みフェーズ
- 横断ルール:
  - 実装は常に現在のフェーズの範囲に限定する。先のフェーズの機能を先回りして作らない
  - モデル名・エンドポイントをコードにハードコードしない
  - LLM の出力は必ず Pydantic で検証してから状態に反映する
  - 設計判断を変えたら `docs/adr/` に記録する
  - 生成テキスト・プロンプトは日本語

### `backend/CLAUDE.md` に書くこと

- よく使うコマンド(`uv sync`、`uv run pytest -m "not integration"`、`uv run ruff check --fix`、`uv run pyright`、CLI の各サブコマンド)
- ディレクトリごとの責務(§2)
- テスト方針: 単体テストでは実 LLM を呼ばない。録画済み応答(`tests/fixtures/`)を使うフェイククライアントを使う。実サーバーを使うテストには `@pytest.mark.integration`
- プロンプトは `prompts/<role>/` に置き、コード内に長い文字列で埋め込まない

### `frontend/CLAUDE.md` に書くこと(Phase 7 で作成)

- API 型は必ず生成物を使い、手書きしない
- ゲーム状態はサーバーのイベントが真実。クライアントは表示用の派生状態のみ持つ
- キャラクター・UI はオリジナルデザインとし、既存作品の模倣をしない

### 進め方

1. 各フェーズの開始時に、このプランの該当節を読み、作業を小さなタスクに分解してから着手する
2. フェーズ完了時に共通完了条件を確認し、ルート `CLAUDE.md` のフェーズ状況を更新する
3. プランと実装の食い違いが出た場合は、実装を優先せずプランの更新を提案する
